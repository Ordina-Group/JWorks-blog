## Introduction

[Kubectl](https://github.com/kubernetes/kubectl){:target="_blank" rel="noopener noreferrer"} is probably one of the more underrated tools in the Kubernetes ecosystem. It's a tool that every beginner start with and seasoned experts use to quickly hack something into a cluster, or more accurately, use to put out a fire during an emergency.

Because of this wide-spread in user profiles using the tool, it packs a lot of goodies under the hood. It can do things as simple as listing all pods in the cluster and showing their status. On the other side of the spectrum are features like `kubectl debug`. 

Very few people need to know the entire CLI reference by heart, but you'll benefit heavily from knowing what gems are available directly from kubectl and don't require any other tooling to be used.

### 101

#### Kubectl get

This is likely one of the first commands you'll use when starting out with Kubernetes. `get`ting resources to see what's running in a cluster. You fetch the information about all resources in your cluster this way, including resources managed by an operator, so call custom resources (based on custom resource definitions). `

The command can be used to simply fetch all pods that are deployed in a cluster as following: `kubectl get pods --all-namespaces`. The short version of the same command would be `kubectl get po -A`. Most common resources in a Kubernetes cluster have a short name (consisting of 2 or 3 letters) next to their normal long name. For pods, this is `po`. The `-A` is a direct replacement for the `--all-namespaces`. 

These are other common short names you can use: 

- `ingress` = `ing`
- `configmap` = `cm`
- `deployment` = `deploy`
- `service` = `svc`
- `replicaset` = `rs`

You can fetch a full list of resources and their short names through `kubectl api-resources`. Note that the output you'll get will differ based on which resources are available in your cluster.

Now the final pro-tip for using the `kubectl get` command. You can combine multiple resource types in a single request. This allows you to fetch all deployments and pods for a given namespace through the following command `kubectl get deploy,po`. The output is simple the concatenation of the output of `kubectl get deployment` and `kubectl get pod`. There is one special macro that can be used here as well: `all`. Contrary to what one would expect, this doesn't fetch all resources for all resource types. It will return a predefined set of resources. 

### Kubectl logs

The next command fetches logs from a running container (not pod) in the cluster. By default, it will fetch the logs of the first container in the pod definition and shows all logs that that container has produced so far. Sometimes the logs might have been rotated partially already by the log manager of the node. The default command is: `kubectl logs <pod-name>`. The output of the commands is naturally highly depending on what the container has outputted. With the `--all-containers` option, all logs for all containers of a single pod can be outputted at once.

You can stream all logs to your machine as they are produced by the container. This can be achived using the `--follow` or `-f` for short flag in the command. The log output can be limitted to just the last 10 lines by adding the option `--tail=10`. Combining these two commands is a useful option when debugging. This way you get a view on the latest few log lines and see all new lines coming in as they are produced. 

As with `get` there are also some powerful mechanisms build into kubectl to extend the normal behavior. The logs command support streaming all logs for a given set of pods. These pods can be selected through a number of ways, mostly linked to a natural grouping. For example, all logs for a deployment can be view by using `kubectl logs deployment/<deployment-name>`. This command will fetch all log and output them. 

As with all commands, these options can be combined into very powerful debugging commands: `kubectl logs deployment/my-deployment -f --all-containers`. This command will streams all logs supporting the my-deployment deployment directly to the users laptop. 

### Kubectl config / context

Any good development platform will have separate environments defined. These environments are typically split from each other by some kind of deployment boundary. This blog won't dive into how these environments are split, but kubectl has some useful commands that can help with switch between the different available clusters. 

`kubectl config set-context --current --namespace <namespace-name>` allows you to set the default namespace all of the following kubectl commands. This prevents you from having to set the namespace explicitly in every command. 

The same structure can be used to switch between clusters (Kube API endpoints). Using `kubectl config use-context <nickname-of-context>` you can set the context you want to use moving forward. The nickname used in the command is the name of the context in your kubeconfig file. 

There are 2 very useful plugins in kubectl that make working with context switching easier. Both can be easily installed through kubectl krew (another superpower we'll discuss later): [kubectx and kubens](https://github.com/ahmetb/kubectx){:target="_blank" rel="noopener noreferrer"}.
