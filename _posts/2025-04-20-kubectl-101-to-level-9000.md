> Mastery isn’t just skill - it’s knowing the right tools and wielding them with precision.

## Introduction

[Kubectl](https://github.com/kubernetes/kubectl){:target="_blank" rel="noopener noreferrer"} is probably one of the more underrated tools in the Kubernetes ecosystem. It's a tool that every beginner start with and seasoned experts use to quickly hack something into a cluster, or more accurately, use to put out a fire during an emergency.

Because of this wide-spread in user profiles using the tool, it packs a lot of goodies under the hood. It can do things as simple as listing all pods in the cluster and showing their status. On the other side of the spectrum are features like `kubectl debug`. 

Very few people need to know the entire CLI reference by heart, but you'll benefit heavily from knowing what gems are available directly from kubectl and don't require any other tooling to be used.

### 101

#### Kubectl get

This is likely one of the first commands you'll use when starting out with Kubernetes. `get`ting resources to see what's running in a cluster. You fetch the information about all resources in your cluster this way, including resources managed by an operator, so call custom resources (based on custom resource definitions). `

The command can be used to simply fetch all pods that are deployed in a cluster as following: `kubectl get pods --all-namespaces`. The short version of the same command would be `kubectl get po -A`. Most common resources in a Kubernetes cluster have a short name (consisting of 2 or 3 letters) next to their normal long name. For pods, this is `po`. The `-A` is a direct replacement for the `--all-namespaces`. 

These are other common short names you can use: 

- `ingress` = `ing`
- `configmap` = `cm`
- `deployment` = `deploy`
- `service` = `svc`
- `replicaset` = `rs`

You can fetch a full list of resources and their short names through `kubectl api-resources`. Note that the output you'll get will differ based on which resources are available in your cluster.

Now the final pro-tip for using the `kubectl get` command. You can combine multiple resource types in a single request. This allows you to fetch all deployments and pods for a given namespace through the following command `kubectl get deploy,po`. The output is simple the concatenation of the output of `kubectl get deployment` and `kubectl get pod`. There is one special macro that can be used here as well: `all`. Contrary to what one would expect, this doesn't fetch all resources for all resource types. It will return a predefined set of resources. 

### Kubectl logs

The next command fetches logs from a running container (not pod) in the cluster. By default, it will fetch the logs of the first container in the pod definition and shows all logs that that container has produced so far. Sometimes the logs might have been rotated partially already by the log manager of the node. The default command is: `kubectl logs <pod-name>`. The output of the commands is naturally highly depending on what the container has outputted. With the `--all-containers` option, all logs for all containers of a single pod can be outputted at once.

You can stream all logs to your machine as they are produced by the container. This can be achived using the `--follow` or `-f` for short flag in the command. The log output can be limitted to just the last 10 lines by adding the option `--tail=10`. Combining these two commands is a useful option when debugging. This way you get a view on the latest few log lines and see all new lines coming in as they are produced. 

As with `get` there are also some powerful mechanisms build into kubectl to extend the normal behavior. The logs command support streaming all logs for a given set of pods. These pods can be selected through a number of ways, mostly linked to a natural grouping. For example, all logs for a deployment can be view by using `kubectl logs deployment/<deployment-name>`. This command will fetch all log and output them. 

As with all commands, these options can be combined into very powerful debugging commands: `kubectl logs deployment/my-deployment -f --all-containers`. This command will streams all logs supporting the my-deployment deployment directly to the users laptop. 

### Kubectl config / context

Any good development platform will have separate environments defined. These environments are typically split from each other by some kind of deployment boundary. This blog won't dive into how these environments are split, but kubectl has some useful commands that can help with switch between the different available clusters. 

`kubectl config set-context --current --namespace <namespace-name>` allows you to set the default namespace all of the following kubectl commands. This prevents you from having to set the namespace explicitly in every command. 

The same structure can be used to switch between clusters (Kube API endpoints). Using `kubectl config use-context <nickname-of-context>` you can set the context you want to use moving forward. The nickname used in the command is the name of the context in your kubeconfig file. 

There are 2 very useful plugins in kubectl that make working with context switching easier. Both can be easily installed through kubectl krew (another superpower we'll discuss later): [kubectx and kubens](https://github.com/ahmetb/kubectx){:target="_blank" rel="noopener noreferrer"}. 

## 201 aka docker cli commands

The following commands will be very similar for people that have experience with using Docker through a CLI. Most of the commands have a direct comparable command in the Docker CLI or are very similar to Docker CLI commands in behavior.

> The following commands are interesting to know, but shouldn't be used on production clusters as they might significantly violate security requirements and repeatability of your deployments. They are however very useful tools for debugging clusters. Some of them even require specific tools to be installed in the container image to work. 

### Kubectl top

This is a very simple command to fetch very basic memory and cpu usage metrics for pods and nodes inside the cluster. This can be very useful in debugging sessions to get a quick overview of the components that are heavily (over) utilising resources in the cluster. 

`kubectl top pod -A` shows a snapshot of the metrics for all pods in a cluster. Use this with caution as for large clusters fetching all pods can be a very large request. 

`kubectl top node` shows the metrics for all nodes in the cluster. By appending a node name, the metrics for a specific node can be fetched. Combined with `kubectl get pod --field-selector=spec.nodeName=<nodeName> -A` this can be an easy way to find issues on a node and which pods are causing it. 


### Kubectl exec

When you're debugging issues in a cluster, it might be very helpful to shell into a container, like you did into VMs in the past, to figure out the environment for example. The command is a direct replica of the capability in the Docker CLI. You can select a pod and container and run an arbitrary command inside the container. There is however one caviat. The container that's executing the command needs to have a shell available. As a shell is opened to execute the command, using the exec command on a rootless or shellless container will outright fail. 

` kubectl exec <pod-name> -c <container-name> -i -t -- bash` will open a bash shell that's being executed directly in the container. 

### Kubectl run

For containers that don't contain a shell, you can't use the exec command. In such a situation another tool might be useful: [kubectl run](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_run/){:target="_blank" rel="noopener noreferrer"}. This command is an easy way to get a quick template for pods. Using this command is/was useful for quickly deploying a container/pod in the cluster to debug network issues in the cluster (e.g. deploy a busybox to test if you can wget google.com). The newer `kubectl debug` command made added a better way of doing this. More on this command later in this blogpost. 

Using `kubectl run -i -t busybox --image=busybox --restart=Never` you can deploy a busybox into your cluster to start hacking away at your issue. 

### Kubectl cp

This command does exactly what you expect it to do. It can copy files to and from containers in your cluster. It uses a similar syntax to rsync and the Docker CLI command. It can be useful to download the running configuration files in a container on the cluster, especially if you do a combination of container image default configuration files, (Helm generated) ConfigMaps and deployment overriden configuration. As with the exec command, there is a specific requirement for `tar` to be available in the container images as the command uses it to stream the files between the container and your local machine. 

`kubectl cp <source-pod-name>:<source-location-in-pod> <target-local-directory-or-file> ` will copy a file or even a full directory from the default container of the specified pod onto your local machine. 

### Kubectl port-forward

This is probably the most powerful commond in this 200 section of the blogpost. This command allows you to connect directly to pods (or services) in a cluster as if they were connected to your local machine. If you're familiar with how SSH port-forwarding works, this is almost identical. It can be really helpful to debug ingress issues and/or when your north-south traffic is broken. 

`kubectl port-forward <pod-name> 8080` creates a port-forward on your local machine from port 8080 towards port 8080 on of the default container of the pod you've selected. Note that this is a blocking command until you close the tunnel again.

### Finalizer cleanup: kubectl edit

This command has been useful in the past to cleanup leftover configuration of a badly behaving operator. Some operators add finalizers to objects to prevent the deletion of objects without the linked or child resources being cleaned properly. A good example could be a database operator that adds a finalizer annotation to the custom database object making sure that the pods, volumes etc. are cleaned up before the custom resource is deleted from the cluster. If for whatever reason, the pods would be deleted while the operator is down, or there is a hickup in the operator which causes the reference to be lost, there will be a reconsiliation issue which causes a limbo state. In this case, and please only in this case, it can be useful to delete the finalizers to allow the kube-api to delete the resources without waiting for the deletion of the non-existing resources. 

`kubectl patch postgresql/some-db --type json --patch='[ { "op": "remove", "path": "/metadata/finalizers" } ]'` will remove the finalizer on the postgresql custom database object and delete the object without waiting for the child resources to be cleaned up.

### KubeCon London 2025 discovery: Headlamp

This blogpost was being written during KubeCon 2025 in London. During one of the keynotes, we learned about [Headlamp](https://headlamp.dev/){:target="_blank" rel="noopener noreferrer"}. It's a web-ui for Kubernetes, supported by the Kubernetes project itself through SIG-UI, that can be installed in a Kubernetes cluster or run locally on a developers machine. It can do most if not all of the features mentioned above. From our initial looks at the project, it looks like a good implementation of the things Lens IDE, Octant and many others tried to achieve over the years. It's especially good to see that it's supported directly from a Kubernetes SIG directly. If you're a developer that needs to use Kubernetes on a daily basis, this might be the best UI for you. 

### Real conclusion

Kubectl is a super powerful tool that has many more feature then most of us initially expected and use on a daily basis. The advanced features can however be a great tool in your toolbox when debugging issues, discovering how certain things work and in general having a better time in managing containers at scale using Kubernetes.

This was the point where we'd intended to plug our favorite TUI for Kubernetes [k9s](https://k9scli.io/){:target="_blank" rel="noopener noreferrer"}, but if Headlamp is as good as it looks on the surface, the necessity to run k9s (however powerful!) might be obsolete.
